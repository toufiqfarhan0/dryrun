## Executive Summary

**Overall Gate: NEEDS REVIEW (WARN) — 68/100**

The codebase is architecturally sound and the test suite is meaningfully structured with good coverage of the core analysis pipeline. No hardcoded credentials, committed secrets, or disk-write zip-slip vulnerabilities were found. The dual-engine fallback (watsonx → deterministic) is well-tested. That said, three gaps warrant attention before a production release:

### 🔴 Critical (3 findings)
1. **No memory size limit on GitHub archive downloads** — `ghRes.arrayBuffer()` buffers the entire response with no cap. A large monorepo request can OOM the serverless function for all concurrent users.
2. **Raw finding evidence injected into the LLM prompt without sanitization** — `f.evidence` and `f.file` (from the uploaded zip) are inserted verbatim, creating a prompt-injection surface.
3. **Two `it.todo` stubs for the highest-risk Watson failure branch** — a Watson HTTP 200 with malformed JSON is untested; the actual runtime behavior is ambiguous.

### 🟡 Medium (6 findings)
- IAM API key interpolated directly into a form body string (should use `URLSearchParams`)
- `jszip` and `@ibm-cloud/watsonx-ai` declared as production dependencies but never called in production code
- GitHub URL fetch path has zero integration test coverage
- `exportPdf()` functional behavior is untested
- `@types/react ^18` while React 19.0.0 is installed
- `dotenv` in `dependencies` instead of `devDependencies`

### 🟢 Low (5 findings)
- TypeScript not distinguished from JavaScript in stack detection
- `CANONICAL_KIMI_FILES` may ghost into user-uploaded city renders
- Dependency graph capped at 10 files × 3 imports (silently truncated for large repos)
- Fan-in counting uses substring matching (inflates SPOF classification)
- `lucide-react@^1.48.0` uses non-standard major versioning — dependency confusion risk worth verifying

The full detailed report with scorecard, all finding bodies, and the complete remediation table is in the artifact above.
